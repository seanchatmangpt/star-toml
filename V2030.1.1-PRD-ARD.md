# star-toml v2030.1.1 — PRD / ARD

**Depends on:** `wasm4pm-compat`

## Product requirement

`star-toml` SHALL be the deterministic boundary that turns raw configuration observations into admitted configuration witnesses suitable for downstream manufacture and actuation decisions.

Its core 2030 product promise is not "parse TOML." It is:

> **Given exact configuration bytes and an exact admission contract, determine whether the configuration may enter O*, emit a typed refusal when it may not, and produce a replayable witness when it may.**

## Required capabilities

1. Preserve exact input identity and deterministic parsing.
2. Validate schema, closed vocabularies, bounds, required fields, cross-field invariants, and declared semantic versions.
3. Distinguish parse failure, semantic refusal, unsupported capability, unavailable dependency, and verifier failure.
4. Produce content-addressed admission witnesses/receipts over stable canonical bytes.
5. Support deterministic replay and tamper detection.
6. Bind admitted configuration to consumer capability/profile identities rather than treating syntactically valid TOML as globally authorized.
7. Expose machine-readable admission results usable by `ggen`, marketplace, AutoFDE, and other control planes.
8. Preserve compatibility with shared structural law from `wasm4pm-compat` where applicable.

## Architecture requirements

```text
raw TOML O
  -> parse
  -> structural validation
  -> semantic/bound validation
  -> admit | typed refuse | unsupported
  -> canonical admitted representation O*
  -> BLAKE3-bound witness
  -> downstream consumer
```

An admission witness confers **configuration standing only**. It never grants marketplace purchase authority, cloud mutation authority, release authority, or BRCE DO authority.

## Acceptance for v2030.1.1

- identical input/contract/toolchain produces identical admitted output and receipt identity;
- malformed and semantically illegal configurations fail closed with stable typed outcomes;
- unknown values in closed vocabularies are not silently defaulted;
- positive and negative fixtures cover every authority-bearing configuration family;
- a tampered configuration or witness fails replay verification;
- downstream systems can require an exact admitted witness instead of reparsing raw configuration independently;
- any generated projections are reproducible from their authoritative source.

## Falsifiers

The architecture is falsified if syntactic validity can bypass semantic admission; if defaults silently manufacture authority-bearing values absent from input; if the same bytes produce different admitted meaning under the same pinned contract; or if consumers cannot bind actions to an exact admission witness.

## Ecosystem contract

`star-toml` manufactures **admission evidence**, not consequences. Raw configuration is `O`; admitted configuration is an input to later manufacture. BRCE remains the only lawful path to consequential DO where that boundary exists.
