\section*{Setup}

\textbf{Crate:} \texttt{praxis-retrofit} (registry orchestration layer)

\textbf{Configuration File:} \texttt{repos.toml}
\begin{lstlisting}
[registry]
name = "fleet-primary"
timeout_ms = 5000

[[registry.providers]]
name = "maven-central"
priority_score = 150  # INVALID: must be 0..=100
url = "https://repo1.maven.org/maven2"

[[registry.providers]]
name = "internal-mirror"
priority_score = 85
url = "https://nexus.internal.example.com"
\end{lstlisting}

\textbf{The Bug:} Registry priority scores determine the order in which Maven artifacts are resolved during fleet retrofit operations. The engineering specification restricts \texttt{priority\_score} to $[0, 100]$ to map cleanly to percentile rankings in scoring functions. A value of \texttt{150} violates this contract, causing:
\begin{enumerate}
  \item Retrofit coordinator silently accepts the config (TOML parses fine)
  \item Scoring algorithm computes percentile: \texttt{150 / 100 = 1.5x normalizer}
  \item Fleet retrofit order becomes non-deterministic: lower-priority repos are queried \emph{before} higher-priority ones
  \item First test fixture detects stale artifacts; build fails in CI but passes locally (cache hit)
\end{enumerate}

\section*{Without Admission}

\textbf{Error Trace (what \emph{would} happen):}

\begin{lstlisting}[language=rust]
// In retrofit_orchestrator.rs, line 342
let score_normalized = provider.priority_score as f64 / 100.0;
// score_normalized = 1.5 (out of acceptable range)

// In percentile_ranker.rs, line 89
fn compute_percentile(score: f64) -> u8 {
  ((score * 100.0) as u8).min(255)  // overflow on cast
}
// Returns: 150 (valid u8) but semantically wrong

// Sorting fails silently:
providers.sort_by(|a, b| {
  compute_percentile(a.priority_score)
    .cmp(&compute_percentile(b.priority_score))
});
// Result: [150, 85] stays in that order
// Expected: [85, 150] after normalization

// Fleet retrofit queries in wrong order:
// 1. maven-central (score=150, priority rank #255) [OK] correct by accident
// 2. internal-mirror (score=85, priority rank #85)  [OK] correct

// But in production with 50 providers, order is unpredictable
\end{lstlisting}

\textbf{Why This Is Bad:}
\begin{itemize}
  \item Configuration is \emph{syntactically} valid TOML
  \item Serde deserialization succeeds (it's just a \texttt{u16})
  \item Error only surfaces when fleet retrofit logic executes
  \item Fleet retrofit is non-deterministic → flaky tests, inconsistent behavior
  \item No audit trail of which config caused the rank order to diverge
\end{itemize}

\section*{With Admission}

The \texttt{praxis-retrofit} config struct implements the \texttt{Validate} trait:

\begin{lstlisting}[language=rust]
#[derive(Debug, Deserialize)]
struct ProviderSpec {
  name: String,
  priority_score: u16,
  url: String,
}

#[derive(Debug, Deserialize)]
struct RegistryConfig {
  name: String,
  timeout_ms: u64,
  providers: Vec<ProviderSpec>,
}

impl Validate for ProviderSpec {
  fn validate(&self, v: &mut Validator) {
    v.check_non_empty("name", &self.name);
    v.check_range(
      "priority_score",
      self.priority_score,
      0..=100,  // -- Enforced constraint
    );
    v.check_predicate("url", &self.url, |url| {
      url.starts_with("http://") || url.starts_with("https://")
    });
  }
}

impl Validate for RegistryConfig {
  fn validate(&self, v: &mut Validator) {
    v.check_non_empty("name", &self.name);
    v.check_range("timeout_ms", self.timeout_ms, 100..=60000);
    v.field("providers", |v| {
      for (i, provider) in self.providers.iter().enumerate() {
        v.index(i, |v| provider.validate(v));
      }
    });
  }
}
\end{lstlisting}

\textbf{Validation Failure (what happens with admission):}

\begin{lstlisting}[language=rust]
// Config loading via TrustedLoader
match TrustedLoader::new()
  .layer_file("repos.toml")
  .load_admitted::<RegistryConfig>()
{
  Ok(admitted) => { /* never reached */ },
  Err(e) => {
    // ValidationErrors collected during validate():
    // [ERROR] providers[0].priority_score
    //   code: out_of_range
    //   value: 150
    //   range: 0..=100
    //   severity: Fatal
    //   location: repos.toml:7
    // Admission Refused (q_config = 0)
  }
}
\end{lstlisting}

\textbf{Prevention Mechanism:}
\begin{itemize}
  \item \textbf{Check Type:} \texttt{Validator::check\_range("priority\_score", 150, 0..=100)}
  \item \textbf{Error Code:} \texttt{out\_of\_range}
  \item \textbf{Severity:} \texttt{Fatal} (admission refuses)
  \item \textbf{Fired at:} Load time, before any business logic executes
  \item \textbf{Guarantee:} If \texttt{AdmittedConfig<RegistryConfig>} exists, all \texttt{priority\_score} values are $\in [0, 100]$
\end{itemize}

\section*{Summary}

Without admission, a single out-of-range field value silently corrupted the fleet retrofit priority ranking, manifesting as flaky tests hours later. The admission model caught the error at load time via a single \texttt{check\_range()} constraint, issued a clear error message, and forced the operator to fix the config before any business logic ran. The witness hash proves which configuration was admitted and which was rejected, creating a permanent audit trail.
